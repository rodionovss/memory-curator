# ADR 002: Delivery contract — query → ranked context cards

## Контекст

Epic #15 (Proactive knowledge delivery). База знаний пассивна: агент должен
сам догадаться вызвать `curator query` — на хакатоне retrieval промах 9/10
(пост-мортем Sprint #2, «доступность ≠ применение»). Доставка решается
слоем relevance gate поверх существующего storage (ADR 001), смена
хранилища не нужна.

Текущий путь запроса: `curator_query` фильтрует факты (type, tags, status,
search), сортирует только по дате, `source_file` в ответе отсутствует,
токен-учёта нет. Usage-телеметрия уже собирается (`retrieval_feedback`,
`~/.curator/usage.json`) — ранжирующие сигналы есть, но не используются.

## Решение

1. **Контракт: query → ranked context cards** (транспорт-агностик).
   - Вход — `ContextQuery`:
     - `trigger` — текст (сообщение агента / контекст темы), по которому
       ищем релевантные факты;
     - `types`, `tags`, `exclude_tags` — опциональные фильтры;
     - `limit` (по умолчанию 3), `token_budget` (по умолчанию 500),
       `relevance_threshold` (по умолчанию 0.4).
   - Выход — список `ContextCard`:
     - `title`, `summary` (content_summary), `tags`, `type`;
     - `status` — в выдачу попадают только `verified` (deprecated
       исключаются, hypothesis — по явному запросу клиента);
     - `source_file` — canonical_file для чтения полного текста факта;
     - `score` (0..1) и `reason` — краткое объяснение, почему карточка
       отобрана (теги / совпадение текста / частота использования).
2. **Ранжирование.** Кандидаты — полный скан verified-фактов (персональная
   база — сотни фактов, скан дёшев). Скоринг: пересечение тегов с
   trigger-свойствами + подстрочное совпадение title/summary/tags +
   usage-сигналы (`count`, recency decay). Порог отсекает кандидатов,
   выше порога сортировка по score, лимит и токен-бюджет ограничивают
   выдачу (оценка размера: символы content_summary / 4, факт ≤ 2000 симв.).
3. **Доставка.** Новый MCP-тул `curator_context(query) -> cards` поверх
   контракта; OpenCode-плагин (точка входа — `curator-reminder.js`) вызывает
   его проактивно. Транспорт не влияет на контракт: тот же контракт можно
   вызывать из любого агента.
4. **Отказ безопасности.** Ошибки retrieval → пустой список карточек и
   предупреждение; сессию агента не ломают.
5. **Ручной fallback остаётся.** `curator_query` / `curator_get` не
   меняются: карточки — проактивный путь, ручной запрос — осознанный.

## Альтернативы

- **LLM-ререйтинг кандидатов** — быстрее теряет независимость от
  транспортного контекста, добавляет латентность и стоимость; закладка
  не делается (детерминированный score дешевле и предсказуем), но контракт
  это не запрещает — LLM-фильтр становится отдельным решением.
- **Push всей базы в контекст** — без порога деградирует и игнорируется;
  отклонено (см. «доступность ≠ применение»).
- **Изменение `curator_query` вместо нового тула** — смешивает ручной
  фильтр-запрос и проактивную доставку; ручной путь остаётся контрактом
  текущих клиентов.

## Последствия

- `source_file` попадает в выдачу (поле уже было в БД).
- Появляется функция подсчёта размера факта — первый токен-учёт.
- Бюджет по умолчанию (500 ток. / 3 карточки) делает delivery предиктивным
  по стоимости сессии.
- Usage-телеметрия становится входом ранжирования: отклонение контекстных
  карточек агентов — сигнал качества выдачи (используется Epic #18).
