# Curator Save Playbook (fast lane)

Пивот 2026-10-03: MCP-церемония (session_capture → approve → update-docs)
заменена одним вызовом CLI `curator save`. Дедуп, валидация, маршрутизация
и журнал аналитики - внутри CLI. 0.5.0: два формата записи - карточка-секция
`###` (upsert по заголовку) и файл-знание (`curator save --doc`).

## Когда срабатывать

- Явная просьба: «сохрани знания», «запомни это», `/curator-save`.
- Проактивно: в сессии выяснено проверенное знание, подтверждённое исходниками,
  логами или устройством. Предложи сохранить одной фразой, не сохраняй без
  подтверждения пользователя.

## Что сохранять

Сохраняй проверенные правила, паттерны, принципы, пользовательский стиль и
решения, если они абстрактны и применимы за пределами текущей задачи.

Не сохраняй фичевые детали, конкретные баги, неподтверждённые гипотезы,
проектные детали и локальные implementation details.

Знания про устройство конкретного проекта (как устроен DI, навигация в
текущем репо) - НЕ в личную базу: им место в docs/ai проекта. Куратор
хранит только переносимое. Если сомневаешься, личное это или проектное -
спроси пользователя до сохранения.

## Выбор формата: карточка или файл-знание

Критерий - самостоятельная ценность знания:

- Знание нужно **отдельно от темы** (кросс-темное правило, принцип,
  паттерн) → **карточка**. Пример: «Переиспользование vs копия: когда
  дублирование дешевле абстракции».
- Знание живёт **только в контексте темы** (грабли, конфиг, как устроен
  инструмент) → **файл-тема**, куда оно ложится секцией или разделом.
  Пример: грабли mihomo существуют только с VPN → файл темы vpn.

Одна тема = один файл = одна причина изменения (SRP). Файл-тема может
содержать и вводную теорию, и карточки-грабли вперемешку - это норма.

### Шаблон файла-темы

```markdown
# <Тема>

Краткая вводная: что это и зачем тебе (2-5 предложений, при наличии).

## <Аспект теории / как устроено>
...

## Грабли
### <Грабля: суть в одну строку>
Симптом: ...
Причина: ...
Решение: ...
```

### Шаблон карточки (content_summary)

Правило. Почему так (причина/риск). Когда применять. Самодостаточно:
через неделю понятно без перечитывания сессии.

## Откуда брать кандидатов - сначала леджер

- Если в сессии ведётся леджер задачи `.opencode/features/<task-id>/progress.md`
  - кандидаты, скорее всего, уже собраны там («Принятые правила», знания в
  записях фаз). Читай леджер, не пересканируй контекст сессии - это и есть
  скорость fast lane.
- Леджера нет - извлекай из контекста сессии.

## Извлечение и фильтрация

Не превращай каждое хорошее наблюдение в кандидат. Сначала найди изменения
понимания: исправленные гипотезы, подтверждённые причины, повторяемые правила
и явно сформулированные пользовательские принципы.

Для каждого возможного вывода выполни пять проверок:

1. **Изменение понимания** - что стало понятно благодаря расследованию,
   проверке или исправлению? Описание сделанного изменения не является знанием.
2. **Доказательство** - какой конкретный фрагмент сессии подтверждает вывод?
   Если подтверждение только повторяет summary или не доказывает причинность,
   отбрось кандидат. Доказательность входит в сам content_summary
   (правило + почему), отдельного поля evidence нет.
3. **Переносимость** - останется ли вывод полезным в другой задаче или проекте?
   Убери имена файлов, API, пути и версии из формулировки.
4. **Атомарность** - описывает ли кандидат ровно одно правило?
5. **Тип утверждения** - Reference (факт), Style (стиль), Tool (инструмент),
   Spec (спецификация). Не повышай гипотезу до verified.

Типичные отказы: «добавили поле X в класс Y», «кажется, причина в X»,
конкретный путь или числовой лимит без общего принципа.

## Формат кандидата (карточка)

- `type` - Reference / Style / Tool / Spec;
- `title` - одна строка, минимум 10 знаков, без `#` в начале;
- `content_summary` - правило + почему + условие применения (шаблон выше),
  2-4 предложения;
- `tags` - короткие поисковые ключи;
- `source_file` - необязательно: путь файла в базе (например
  `reference/architecture.md`), если тематический файл уже очевиден.
  Передавай, когда знаешь куда; без него маршрут уходит в дефолт
  `session/*.md`, и знание оседает не там.

Знания из отдельной темы со своей папкой вне базы - уточни у пользователя,
куда их положить (например, тема-проект живёт отдельной папкой в базе -
`vpn/` - и это нормально).

## Сохранение карточек - один вызов CLI

```bash
curator save --yes <<'EOF'
[
  {
    "type": "Reference",
    "title": "...",
    "content_summary": "Правило. Почему. Когда применять.",
    "tags": ["...", "..."],
    "source_file": "reference/<тема>.md"
  }
]
EOF
```

CLI выводит: одобренные с маршрутом (строки «✅ название … → файл.md»),
отклонённые gatekeeper'ом с причинами (дубликаты, формат). После записи CLI
сам делает локальный git-коммит базы (push не выполняется никогда) - это
страховка отката для автоматических правок. Прочитай вывод
и покажи пользователю итог: что и куда сохранено, что отсеялось.

Принцип показа: **показ и сохранение одним ходом** - не жди отдельного «ок»
после показа итога. Пауза до записи - только если маршрут неоднозначен
(личное vs проектное) или знание - непроверенная гипотеза.

## Сохранение файла-знания - write + фиксация

Контент пишет модель, куратор - библиотекарь (проверка полки + git +
журнал аналитики):

1. Прочитай целевой файл темы (если существует) - не дублируй уже
   записанное.
2. Запиши/дополни файл в базе по шаблону файла-темы; путь должен
   совпадать с таргетом карты `knowledge-map.md` (или лежать в session/).
3. Зафиксируй:

```bash
curator save --doc vpn/mihomo.md
```

Куратор сверит путь с картой (мимо карты - отказ с подсказкой таргетов),
сделает git-коммит и запишет событие в журнал аналитики. В SQLite ничего
не пишется - файл сам себе единица.

## Корректировки

Пользователь просит поправить формулировку → внеси правку в title/summary
и вызови `curator save --yes` повторно. Совпадающий title = обновление
существующей секции (upsert), не дубль. Покажи исправленный итог.

## Когда НЕ вызывать запись

- Сессия в plan/read-only режиме - предложи, но скажи: «сохраню после
  переключения сессии в режим записи».
- Знание не прошло фильтры (гипотеза, проектная деталь) - объясни почему,
  кандидат не создавай.
