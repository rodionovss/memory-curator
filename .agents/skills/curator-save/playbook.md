# Curator Save Playbook

## Когда срабатывать

- Явная просьба: «сохрани знания», «запомни это», `/curator-save`.
- Проактивно: в сессии выяснено проверенное знание, подтверждённое исходниками,
  логами или устройством. Предложи сохранить его, но не сохраняй без
  подтверждения пользователя.

## Что сохранять

Сохраняй проверенные правила, паттерны, принципы, пользовательский стиль и
решения, если они абстрактны и применимы за пределами текущей задачи.

Не сохраняй фичевые детали, конкретные баги, неподтверждённые гипотезы,
проектные детали и локальные implementation details.

## Извлечение и фильтрация

Не превращай каждое хорошее наблюдение в кандидат. Сначала найди изменения
понимания: исправленные гипотезы, подтверждённые причины, повторяемые правила
и явно сформулированные пользовательские принципы.

Для каждого возможного вывода выполни пять проверок:

1. **Изменение понимания** - что стало понятно благодаря расследованию,
   проверке или исправлению? Описание сделанного изменения не является знанием.
2. **Доказательство** - какой конкретный фрагмент сессии подтверждает вывод?
   Если evidence только повторяет summary или не подтверждает причинность,
   отбрось кандидат.
3. **Переносимость** - останется ли вывод полезным в другой задаче или проекте?
   Локальный эпизод можно обобщить только если в сессии явно названы правило,
   причина, риск или урок. Убери из summary имена файлов, API, пути, PR и
   версии. Не выводи принцип только из устройства текущего репозитория.
4. **Атомарность** - описывает ли кандидат ровно одно правило? Раздели
   независимые выводы, не склеивай их в одну карточку.
5. **Тип утверждения** - это проверенный факт, стиль, инструментальный совет
   или спецификация? Не повышай гипотезу до verified.

Допустимо вывести из подтверждённого локального эпизода общий принцип, например:
из риска самостоятельного `auto_approve` вывести «approval должен быть отдельным
шагом протокола». Недопустимо сохранять название параметра, класс, путь или
числовой лимит как универсальное правило.

Типичные отказы:

| Материал | Причина отказа |
|---|---|
| «Добавили поле X в класс Y» | деталь текущего изменения |
| `OrderedDict`, SQLite или конкретный путь репозитория | implementation/project detail |
| «Вызвать метод A перед B в этом API» | локальный контракт без общего принципа |
| «Кажется, причина бага в X» | гипотеза без проверки |
| «Этот PR надо смержить вручную» | решение текущего процесса |

## Режим сессии

Если сессия в plan/read-only режиме, извлекай и показывай preview, но не
вызывай `curator_session_capture` до выхода в режим исполнения. Подтверждение
пользователя не снимает этот запрет. Скажи: «Кандидаты готовы, сохраню после
переключения сессии в режим записи».

## Формат кандидата

Для каждого прошедшего фильтр кандидата подготовь:

- `type`;
- `title` - одна строка, минимум 10 знаков;
- `content_summary` - 1-2 предложения;
- `tags`;
- `evidence` - цитата из сессии.

Заголовок не начинается с `#` и не содержит перевод строки. Описание не
содержит строк, начинающихся с `#`, `*Тип:*` или `*Теги:*`. Теги не содержат
`|` и `,`. Gatekeeper отклонит нарушения формата.

## Сохранение

### Preview

Показывай candidates нумерованным списком. Для каждого используй ровно такой
порядок полей:

```text
1. Название знания
Type: Reference
Rule: ...
Why: ...
Evidence: ...
Tags: ...
```

`content_summary` формируй как две смысловые части `Rule` и `Why`. `Evidence`
нужно для проверки происхождения кандидата и локального evaluation log, но не
включай его в `content_summary` и не сохраняй как часть общего знания. `Tags`
остаются короткими поисковыми ключами.

1. Вызови `curator_status` и выбери тип по его описанию, а не по догадке.
   Неизвестный тип передавай только с `new_type=true` и
   `type_description`, после решения пользователя.
2. Вызови `curator_query` с релевантными ключевыми словами и убери дубликаты.
3. Вызови `curator_session_capture` с кандидатами без `auto_approve` и
   `source_file`. Для read-only сессии не вызывай тул до переключения в режим
   записи.
4. Покажи preview каждого кандидата: `candidate_id`, тип, заголовок, summary,
   теги и evidence. Не вычисляй здесь target-документы, Markdown-патчи или
   placements. Спроси: все, отдельные ID или отказ.
5. После выбора вызови `curator_capture_approve` только с `capture_id` и
   выбранными `candidate_id`. Manifest ответа неизменяем; candidates повторно
   не отправляй.
6. Если ответ имеет `status=update_project_docs` и
   `next_action=curator-update-docs`, загрузи `curator-update-docs` и передай
   ему `capture_id`, `base_dir`, `map_path` и `facts` из manifest. Этот skill
   сам выполнит preflight, semantic write-back и один вызов
   `curator_capture_complete`.
7. Успех объявляй только при точном ответе `status=completed`. В случае
   `cancelled` или `error` покажи причину без повторной записи.
