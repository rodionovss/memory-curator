# Experiment 02: Access Path — результаты

Дата: 2026-09-17. 192 прогона: 8 задач × 4 руки × 2 модели × 3 повтора.
Routing зафиксирован = R3 (победитель 01). P0 — переиспользование R3-прогонов
01 (конфигурация идентична: routing + файлы, без curator).

## Главные результаты

**Application (pass) по рукам и моделям:**

| Рука | strong | weak | median tokens |
|---|---:|---:|---:|
| P0 файлы | 23/24 | 17/24 | 18.1k |
| P1 + curator MCP | 24/24 | 16/24 | **26.2k** |
| P2 + каталог-для-запросов | 24/24 | 16/24 | 20.5k |
| P3 oracle-факт в context | 24/24 | 17/24 | 20.5k |

**Вызовы curator (manual_curator_query/get) за все 192 прогона: 1.**

## Выводы

1. **Агент никогда не вызывает curator сам.** Даже когда MCP-инструменты
   доступны (P1), и даже с каталогом «тема → curator query» (P2): 0-1 вызовов
   из 96 прогонов каждой руки. Пассивная доступность инструмента не
   работает — «доступность ≠ применение» воспроизведён на уровне тулов.
   Дефиниции curator-инструментов при этом стоят ~8k токенов контекста
   (P1: 26.2k vs P0: 18.1k median) — чистый overhead без единого вызова.
2. **Access path не двигает application при живом routing.** С R3-роутингом
   слабая модель: P0 17/24 → P3 17/24. Добавка curator/индекса/oracle поверх
   работающего routing не даёт прироста.
3. **Oracle-факт помогает только там, где routing не справляется:**
   T01 (скрытая ловушка) 3/6 → 5/6. Цена: лёгкий шум на консенсусных
   задачах (T07: 6/6 → 4/6) и no-memory контроле (K1: 6/6 → 4/6).
4. **Strong-модель на потолке** (23-24/24 во всех руках) — дифференцировать
   access paths на ней невозможно.

## Следствие для архитектуры

- Резидентный MCP curator в контексте агента — неиспользуемый балласт:
  проблема доставки решается routing-слоем (01) и качеством retrieval (04),
  не доступностью инструментов. Вердикт по судьбе MCP-слоя — ADR 003
  (issue #33) после эксперимента 03.
- Проактивная доставка имеет смысл только как замена несамостоятельного
  вызова: карточка должна приходить сама (03), а не ждать инициативы агента.
