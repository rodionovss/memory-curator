# Memory Experiments Runbook

Версия протокола: `1.0`

Этот каталог содержит воспроизводимые эксперименты, которые отвечают на
четыре разных вопроса. Не смешивать их результаты в одну метрику.

## Порядок запуска

1. `01-routing-format.md` - проверить, какой формат указателя направляет
   агента к нужному знанию.
2. `02-access-path.md` - проверить, нужен ли агенту curator, компактный
   индекс или уже найденный факт.
3. `03-proactive-delivery.md` - отделить пользу правильной карточки от
   качества реального retriever-а.
4. `04-storage.md` - сравнить Markdown search и SQLite search отдельно от
   поведения модели.

Не запускать live A/B на случайных рабочих сессиях до выполнения первых
трёх протоколов. В случайной сессии может не быть применимого факта, и тогда
нулевая application rate ничего не говорит о качестве delivery.

## Общие определения

### Routing

Модель увидела задачу и выбрала, куда идти за памятью: не идти, открыть
указатель, прочитать source file или вызвать Curator.

### Retrieval

Механизм вернул конкретный факт из corpus.

### Application

Детерминированная проверка решения показывает, что факт повлиял на результат.
Одного упоминания факта или чтения файла недостаточно.

### Memory opportunity

Для задачи заранее известен релевантный fact ID. Если подходящего факта нет,
задача не используется для расчёта application rate, но используется для
проверки false positive.

### Источник знания

Каждое событие получает одно из значений:

| Значение | Смысл |
|---|---|
| `baseline_system` | текст уже был в системном контексте (`AGENTS.md`, Personal Setup) |
| `index_read` | модель прочитала индекс/карту |
| `source_file_read` | модель прочитала файл с полным фактом |
| `manual_curator_query` | модель сама вызвала `curator_query` |
| `manual_curator_get` | модель сама запросила конкретный факт |
| `index_in_context` | компактный каталог был заранее добавлен в context |
| `proactive_card` | система добавила полный факт в context |

Если путь состоит из нескольких этапов, записать все этапы, например:
`baseline_system -> index_read -> manual_curator_query`.

## Общие правила выполнения

- Один запуск = одна свежая сессия агента.
- После каждого запуска удалить рабочую директорию и создать её из fixture.
- Не менять prompt, corpus, model, temperature и checks внутри одного варианта.
- Запрещено подсказывать модели, какой вариант сейчас запущен.
- Варианты с доступом к Curator получают одинаковые tool descriptions.
- Файл с полным фактом не должен случайно попасть в system prompt варианта,
  где разрешён только указатель.
- Все результаты сохранять в JSON по схеме `schemas/run.json`.
- Решение `PASS/FAIL` брать из deterministic check, а не из ответа модели.
- Для неоднозначных случаев добавлять `review_status: manual_review`, но не
  менять автоматически итоговый score.

## Модели и повторы

Основной прогон выполняется на двух моделях:

- `strong` - текущая рабочая модель;
- `weak` - выбранная более слабая модель того же harness-а.

Для routing/access/proactive: 8 задач × 3 повтора × все варианты × 2 модели.
Повтор получает новый session ID и свежую рабочую директорию.

Для storage модель не нужна: это backend benchmark, 20 запросов × 5 повторов
на backend.

## Артефакты

Каждый протокол обязан сохранить:

```text
results/<experiment>/<run-id>.json
results/<experiment>/summary.json
results/<experiment>/README.md
```

`summary.json` содержит counts, rates, confidence intervals и список
непрошедших checks. Сырые private session transcripts не коммитить.

## Как читать результат

- Сначала проверить, что все deterministic checks прошли.
- Затем сравнить routing, retrieval и application отдельно.
- Не считать отсутствие вызова Curator ошибкой на задаче без memory
  opportunity.
- Не считать чтение карточки применением.
- Не считать совпадение слов доказательством применения без check.
- Нулевой live application rate при нулевом числе memory opportunities не
  является отрицательным результатом.

## Общий формат вывода

Для каждого эксперимента в `summary.json` обязательно указать:

```json
{
  "experiment": "routing-format",
  "runs": 192,
  "models": ["strong", "weak"],
  "variants": ["R0", "R1", "R2", "R3"],
  "primary_metric": "application_rate",
  "rates": {},
  "confidence_intervals": {},
  "failures": [],
  "decision": "..."
}
```

`decision` заполняется только после проверки количества запусков и coverage.
