# Application Benchmark: применение vs доступность знаний

Эксперимент дня 2 спринта (06.09.2026). Отвечает на вопрос критерия №2:
**помогает ли база знаний агенту применять правила там, где локальный код ведёт к ошибке?**

Полная методология и честные кейваты: `results/report.md`.

## Дизайн: три руки, одинаковое задание

| Рука | Доставка знания |
|------|-----------------|
| A (baseline) | ничего; абляция «внешняя база отключена» |
| B (pull/статика) | замороженная копия всей базы (66 verified-фактов, 11 тематических .md) + «консультируйся по необходимости» |
| C (push/куратор) | карточка правила, подобранная retrieval-поиском куратора и инжектированная в промпт |

Испытуемые — чистые сабагенты (свежий контекст на каждый прогон), N=1 на ячейку основного прогона; дискриминирующие задачи реплицированы ×3.

## Задачи

12 фикстур в `fixtures/`: 10 задач-ловушек (T01–T10, каждая кодирует одно правило из базы; правило в задании не названо, ловушка — в legacy-коде или документации вокруг) + 2 контроля (K1 — тривиальная без применимого знания; K2 — законное применение, где правило применять НЕ надо).

## Результат

| | A | B (статика) | C (куратор) |
|---|---|---|---|
| Основной прогон (10 задач) | 8/10 | 9/10 | **10/10** |
| Дискриминаторы с репликацией (T01+T06, N=3) | 0/6 | 3/6 | **6/6** |
| Контроли K1/K2 | PASS | PASS | PASS |

Fisher exact (A vs C, дискриминаторы): **p = 0.0011**.

Ключевой кейс T01 («следуй существующему стилю файла», где весь файл оборачивает suspend-DAO в `withContext`):
агент B имел всю базу и повторил антипаттерн во всех 3 повторах — доступность знания не равна его применению.
Агент C применил правило 3/3.

## Структура

```
fixtures/   task.md + fix/ — стартовое состояние задачи (нейтральный синтетический код)
checks/     детерминированные проверочные скрипты (grep/структура)
            FROZEN-original.sha — чеки на момент до прогонов (2 extraction-бага исправлены пост-хок, см. report.md)
            FROZEN-fixed.sha   — чеки, использованные для финального скоринга
results/    report.md — полная методология и кейваты
            scoring-main-run.txt, scoring-replication.txt — выводы скоринга
            solutions/ — снимки решений всех рук для независимой верификации
```

## Воспроизведение

Чеки детерминированы и не используют LLM:

```bash
cd checks
# решения рук лежат в ../results/solutions/<task>/<arm>/
python3 -c "
import sys; sys.path.insert(0, '.')
from pathlib import Path
import importlib
BASE = Path('../results/solutions')
for t in ['T01','T06']:
    mod = importlib.import_module('check_'+t)
    for run in [t, t+'R2', t+'R3']:
        r = [mod.check(BASE/run/a)[0] for a in ['arm_a','arm_b','arm_c']]
        print(run, r)
"
```

Полный ре-ран с живыми агентами: развернуть фикстуры в три директории на руку
(`cp -R fixtures/T01/fix/. <arm_dir>/`), дать одинаковые задания с промптами рук
(формулировки — в report.md), решения прогнать чеками.

## Заметки о валидности

- База знаний в репо не входит (рабочие знания команды). В прогоне руки B использовалась
  замороженная копия 66 verified-фактов, извлечённых майнингом из 100 реальных рабочих
  сессий (см. корневой README, раздел mining).
- N=1 на ячейку основного прогона; значимость обеспечивают репликации дискриминаторов.
- 8 из 10 задач консенсусны для сильной модели — дельта системы проявляется на
  не-консенсусных правилах, противоречащих локальному контексту.
- Экспериментатор — автор задач и чеков; чеклист заморожен до прогонов (FROZEN-original.sha).
