# Документация предметной области

Правила использования документации предметной области при изучении кодовой базы инженерными навыками.

## Что прочитать перед изучением кодовой базы

- Корневой файл **`CONTEXT.md`** или
- корневой файл **`CONTEXT-MAP.md`**, если он существует: он указывает на отдельные файлы `CONTEXT.md` для каждого контекста. Прочитай все файлы, относящиеся к текущей теме.
- **`docs/adr/`**: прочитай записи архитектурных решений, относящиеся к области предстоящей работы. В многоконтекстных репозиториях также проверь `src/<контекст>/docs/adr/` на наличие решений конкретного контекста.

Если каких-либо файлов нет, продолжай работу без отдельного уведомления и предварительного предложения их создать. Навык `/domain-modeling`, вызываемый через `/grill-with-docs` и `/improve-codebase-architecture`, создаёт их по мере необходимости, когда уточняются термины или принимаются решения.

## Структура файлов

Одноконтекстный репозиторий, используемый в большинстве случаев:

```text
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Многоконтекстный репозиторий определяется наличием `CONTEXT-MAP.md` в корне:

```text
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← общесистемные решения
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← решения конкретного контекста
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## Используй лексику глоссария

Когда в результате работы называется понятие предметной области — в заголовке задачи, предложении по рефакторингу, гипотезе или имени теста — используй термин из `CONTEXT.md`. Не заменяй его синонимами, которые глоссарий явно отклоняет.

Если нужного понятия в глоссарии нет, проверь, действительно ли проект использует предлагаемый термин. Реальный пробел в общей лексике зафиксируй для `/domain-modeling`.

## Отмечай противоречия архитектурным решениям
