# Memory Curator — Контур самоулучшения

> Куратор улучшает память агента (improve-цикл внутри ядра). Этот сценарий —
> как сделать так, чтобы улучшался и сам куратор: баги и идеи от любых агентов
> собираются в GitHub Issues, а разбирает их один уполномоченный мейнтейнер.

## Проблема

Любой агент в любой сессии, заметив баг куратора, хочет «быстро починить».
Несанкционированная правка живой системы памяти ломает все сессии сразу.
А единственный разработчик не хочет быть узким горлом: репорты должны
копиться и разгребаться фоном.

## Механизм (три роли, 0 правок ядра)

```
любая сессия ──(скилл-репортёр)──> GitHub Issues
                                          |
                                cron / вручную
                                          |
                                скилл-мейнтейнер (CURATOR_MAINTAINER=1):
                                  триаж → крит-баг: fix-ветка + тесты + лок. коммит
                                          |
                                отчёты (ops/reports/) + уведомление
```

1. **GitHub Issues** (`gh issue create`): лейблы `crit-bug` |
   `improvement`, в теле — дата, сессия, проблема, пруф. Создавать может
   любой агент, статусы и закрытие — только мейнтейнер. Отдельно от
   продуктового роадмапа (`design/backlog.md`); дубли против него
   проверяются при триаже.
2. **Скилл-репортёр** (загружается в любой сессии): заметил баг/идею —
   создай issue с пруфом, НЕ правь репо. Даёт импульсу «починить»
   легальный выход.
3. **Скилл-мейнтейнер** — единственный с правом правки. Цикл:
   триаж (дубль / нет пруфа / крит / доработка) → крит-баг: воспроизведи,
   fix-ветка от main, тесты, локальный коммит с «(fixes #N)» →
   сводный отчёт + уведомление. Вопросы, которые нельзя решить без
   человека, — в отчёт, решения не принимает сам.

## Расположение (единый источник истины)

Всё по куратору живёт в этом репозитории: код, роадмап
`design/backlog.md`, решения `design/decision-log.md`, баги — GitHub
Issues. Операционная механика лупа (раннер, скиллы репортёра/мейнтейнера,
отчёты, логи) — в локальной gitignored-папке `ops/` внутри клона: она
личная, клиентам продукта не нужна (decision-log №14). Скиллы
curator-feedback / curator-maintainer в `.agents/skills/` не публикуются.

## Гварды

- Мейнтейнеру **запрещён `git push`** всегда; мерджи в main — решение
  человека. Issue закрывается сама, когда fix-ветка с «fixes #N» доезжает
  до main.
- `main` не трогается: правки только в `fix/*`-ветках.
- **pre-commit hook**: коммит без env `CURATOR_MAINTAINER=1` блокируется —
  структурная отсечка «случайного» агента (не защита от намеренного
  обхода: агенты работают от одного пользователя ОС).
- Живая БД куратора — только после бэкапа.
- Инструкция-гейт в корне репо (AGENTS.md/CLAUDE.md): «ты не мейнтейнер →
  пиши issue» — агент читает её в момент, когда открыл репо.

## Интеграция по расписанию

Пример — cron на macOS (launchd): обёртка `ops/run-maintainer.sh` раз в
день проверяет открытые issues; нет — тихий выход; есть — запускает
неинтерактивную сессию мейнтейнера из корня репо. Обёртка ставит
`CURATOR_MAINTAINER=1` и проверяет, что после прогона появился свежий
отчёт в `ops/reports/` (иначе — помечает прогон провальным, даже если
процесс вышел с rc=0).

Нюансы неинтерактивных сессий: агент не может задавать вопросы — всё
неоднозначное уходит в отчёт; доступ launchd к `~/Documents` регулируется
TCC macOS.

## Известные ограничения

- Гейты — контракты + hook, а не права ОС: защищают от несчастного случая,
  не от злоумышленника. Полноценный RBAC осознанно отвергнут
  (decision-log №12).
- Скилл-репортёр — промпт-контракт поверх `gh` CLI; серверный тул приёма
  репортов отвергнут (decision-log №13).
